# خطة التكامل البصري — واجهة مرتبة ومتصلة بالباكند

> **التاريخ:** 2026-11-20
> **الهدف:** مظهر بصري موحّد، مرتب، RTL-first، ومتصل بالبيانات الحقيقية للباكند
> في كل شاشة، دون إعادة كتابة شاملة للواجهات.
> **القاعدة:** لا بيانات وهمية في الواجهة، ولا كود باكند جديد بدون اختبار.

---

## 1. الوضع الحالي (مُقاس من الكود)

| العنصر | العدد الفعلي |
|---|---|
| قوالب أدمن HTML | 40 |
| ملفات JS أدمن | 24 (22 منها تستخدم `OrionAPI`) |
| قوالب متجر HTML | 10 |
| ملفات JS متجر | 6 |
| نقاط API (decorators) | ~100 |
| دوال API/service | ~211 |
| ملفات E2E | 3 مسارات + لقطات شاشة |

**ما يعمل أصلاً:**
- صفحات المتجر (الرئيسية/المنتج/التصنيف) تستقبل بيانات حقيقية من `ProductService` / `CategoryService` عبر `engine/routes.py`.
- معظم شاشات الأدمن تُحمّل بياناتها ديناميكياً عبر `OrionAPI` + `SafeDOM`.
- ثيم كحلي/ذهبي محلي + Tailwind مبني + تدقيق RTL/WCAG آلي + E2E.

**الفجوات الحقيقية (ما ستعالجه الخطة):**
- بطاقات لوحات التحكم تعرض أرقاماً **حقيقية** من `/platform/stats` و`/tenant/dashboard`
  (تصحيح: الأصفار في اللقطة كانت من قاعدة فارغة، لا قيمة ثابتة)، لكن بلا loading/تنسيق موحّد،
  ولا اختبار يغطّي `/platform/stats`.
- لا يوجد **shell موحّد** (هيدر/تنقل/فتات خبز/حالة تحميل) عبر الـ 40 قالباً.
- لا **حالات تحميل/فراغ/خطأ** موحّدة عند فشل الـ API.
- لا **مكوّنات** مشتركة للجداول والنماذج — كل صفحة تعيد اختراع التنسيق.
- لا **توasts/تأكيد** موحّدة لعمليات الحذف/الحفظ.
- لا **خريطة تغطية**: أي شاشة تستخدم أي endpoint (يصعب اكتشاف الانقطاع).

## 2. المبادئ الحاكمة

1. كل قيمة في الواجهة تأتي من API أو من قالب مُمرَّر من الباكند — **لا أرقام/أسماء ثابتة**.
2. أي حاجة لبيانات جديدة تُضاف كـ **endpoint صغير** في `05-API/v1` مع اختبار، لا تُختلق في JS.
3. كل endpoint جديد يحترم `g.tenant_id` وRLS (سياق المستأجر مُطبَّق في middleware).
4. **RTL-first**: خصائص منطقية (`inset-inline-*`, `margin-inline-*`) بدل `left/right`.
5. مكوّنات CSS موجودة في `orion-theme.css`، والبناء عبر `npm run build:css` — لا CDN.
6. كل بند يُغلق بـ: اختبار + لقطة شاشة + pre-commit أخضر.

## 3. البنود (بالترتيب — بند بند)

### البند 1 — توثيق نظام التصميم (Design System Doc)
**الهدف:** مرجع واحد للألوان/المسافات/المكوّنات.
- أنشئ `docs/UI-DESIGN-SYSTEM.md` يشرح: المتغيّرات، متى تستخدم `orion-card` / `orion-btn` / `orion-table` / `orion-badge`، قواعد RTL، التباين WCAG AA.
- أضف **صفحة معاينة مكوّنات** (قالب `ui_kit.html` + route في `tenant_admin/routes.py`) تعرض كل مكوّن بحالاته.
**DoD:** الوثيقة موجودة؛ صفحة المعاينة تُفتح في E2E؛ `audit_a11y --check` أخضر.

### البند 2 — Shell موحّد للوحة الإدارة
**الهدف:** هيدر/شريط جانبي/فتات خبز/مستخدم متسق في كل شاشة.
- حدّث `admin_base.html` و`components/sidebar.html` لإضافة:
  - شريط علوي: اسم المتجر/المنصة + breadcrumb ديناميكي من `active_nav`.
  - منطقة إجراءات صفحة (-page actions) قابلة للحقن عبر `{% block page_actions %}`.
  - حالة "مستخدم/مستأجر" واضحة مع رابط ملف شخصي/خروج.
- لا تغيير في الـ 40 قالباً بعد — فقط الـ shell (التوريث سيطبّق تدريجياً).
**DoD:** لقطة لوحة المتجر + لوحة المنصة تُظهر الهيكل الموحّد؛ 3 مسارات E2E لا تزال ناجحة.

### البند 3 — طبقة بيانات الواجهة (API client موحّد)
**الهدف:** تعامل واحد مع التحميل/الخطأ/النجاح لكل الـ 24 ملف JS.
- راجع `07-ADMIN/static/js/api_client.js` و`OrionAPI`:
  - توحيد `request()` مع `AbortController`، timeout، فك رسالة الخطأ من `OrionError`.
  - `withLoading()` + `toast()` + `confirmDanger()` في `admin_utils.js` (SafeDOM فقط).
  - منع تكرار الطلبات (dedupe) لعمليات الحفظ.
- عدّل 2–3 ملفات JS كنموذج ثم عمّم تدريجياً.
**DoD:** اختبار وحدة/JS يغطي الحالات الثلاث؛ لا `innerHTML`؛ لا استدعاء `fetch` مباشر خارج client في الملفات المُحدَّثة.

### البند 4 — لوحات التحكم: عرض البيانات الحقيقية باحتراف
**الهدف:** تحسين عرض البيانات الموجودة فعلاً لا اختراع endpoints جديدة.
- Endpoints موجودة ومُصلَّحة بالفعل: `GET /api/v1/tenant/dashboard` و`GET /api/v1/platform/stats`
  (كلاهما محمي بصلاحية مناسبة ويحترم RLS).
- حسّن `platform_dashboard.html` و`tenant_dashboard.html`:
  - بطاقات `.orion-card` + `.orion-stat` مع تسميات واضحة.
  - عنصر `.orion-skeleton` أثناء التحميل، وحالة فراغ/خطأ بدل نص فارغ.
  - `aria-live="polite"` على قيم الأرقام، وتنسيق أرقام محلي (`toLocaleString`).
- أضف اختبار تكامل لـ `/api/v1/platform/stats` (الوحيد غير المغطّى) يتحقق من الأرقام
  بعد إنشاء متاجر/مستخدمين فعليين.
**DoD:** اللقطة تُظهر أرقاماً حقيقية بتنسيق محلي + skeleton؛ اختبار endpoint ناجح.

### البند 5 — مكوّنات مشتركة للقوالب (CSS فقط، بلا إعادة كتابة)
**الهدف:** مظهر مرتب لـ 40 قالباً بأقل تعديل.
- أضف إلى `orion-theme.css`: أنماط `.orion-toolbar`، `.orion-form-grid`، `.orion-empty`، `.orion-skeleton`، `.orion-stat`.
- طبّق على **أهم 10 شاشات** أولاً (dashboards، products، orders، tenants، users، gateways، tax، subscriptions، returns، financial report).
- أعد بناء Tailwind (قد تختفي أصناف غير مستخدمة).
**DoD:** لقطات قبل/بعد لـ 5 شاشات؛ لا تنسيق مضمّن جديد (`style=`) في الملفات المُحدَّثة.

### البند 6 — قوالب المتجر (10 صفحات) بلمسة أخيرة
**الهدف:** تجربة تسوّق متسقة مع الباكند.
- `index/product/category`: بطاقات منتج موحّدة + صورة بديلة عند الغياب + سعر/توفر من الحقول الحقيقية.
- `cart/checkout`: ملخص الطلب من `StoreAPI`، حالات تحميل/خطأ، رسالة نجاح واضحة، زر ذهبي موحّد.
- `account`: نموذج دخول/تسجيل حقيقي عبر `/api/v1/auth` (لا حقول معزولة).
**DoD:** E2E موسّع يتحقق من ظهور منتج حقيقي + سعر + إضافة للسلة؛ لقطات تحديث.

### البند 7 — التغطية الشاملة وباقي الشاشات
**الهدف:** لا صفحة "نصف منتهية".
- أنشئ `scripts/audit_ui_coverage.py`: يقرأ كل قالب، ويستخرج مسارات API المستخدمة، ويقارنها بـ `API_BLUEPRINTS` → تقرير "شاشة بلا مصدر بيانات".
- راجع أعلى 10 فجوات واربطها بالـ endpoints الموجودة بدل إضافة جديدة.
**DoD:** التقرير يعمل في CI؛ صفر شاشة حرجة بلا مصدر بيانات موثّق.

### البند 8 — الجودة البصرية النهائية
**الهدف:** منع الانكسار المستقبلي.
-وسّع E2E إلى 8–10 لقطات (أهم الشاشات) مع نفس فحص أخطاء JS.
- أضف فحص تباين ألوان آلي للـ design tokens (WCAG AA ≥ 4.5 للنص).
- حدّث `docs/LAUNCH-CHECKLIST.md` بنتائج البصرية.
**DoD:** كل اللقطات محفوظة، `audit_a11y` أخضر، pre-commit أخضر، الاختبار الكامل أخضر.

## 6. ملاحظة تنفيذية
هذه خطة **تكامل وتنسيق** لا إعادة بناء: لا تغيير في قاعدة البيانات ولا في منطق الأعمال،
إلا endpoints مجمّعة صغيرة في البند 4 مشمولة بالاختبارات. النشر الفعلي يبقى خارج النطاق.
